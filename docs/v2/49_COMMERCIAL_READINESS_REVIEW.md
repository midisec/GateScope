## 1. 结论

当前已经具备比较完整的单机行情研究与模拟交易能力，可作为受控内测的产品基础；但还不能视为完整的自助式商业 SaaS，更不能据此承诺 TradingView 级规模或稳定盈利。

更合适的近期产品定位是“形态研究、可追溯分析、AI 辅助研判与模拟交易复盘”。优先补齐用户自助流程、计量与资源公平、恢复能力和真实表现复盘，不宜先增加大量指标、复制社交社区或启用实盘。

已经做过的能力不要重复建设：后台自选采集、形态生命周期及失败案例、历史比较、年度分片研究、共享资金组合回测、Web/MCP 共用 PAPER 账本、真实公开盘口的保守模拟成交、原始证据图、订单分页、TG 查询、近期校准及独立 PAPER 业务循环。具体实施与验证边界见 [48_PLATFORM_OPTIMIZATION.md](./48_PLATFORM_OPTIMIZATION.md)。

## 5. P1：提升用户实际使用价值

### 5.1 交易复盘中心与前瞻观察项目

已有原图、依据、成交、费用、研究和影子观察，不必再做一套账本。新增跨记录复盘：原计划 → 是否可成交 → 实际均价/部分成交 → 退出 → 净损益，区分判断、滑点、延迟、未成交和人工变更。按冻结的形态/策略/模型版本比较，旧单没记录的依据仍显示未关联，不能补造标签。

当前结构和指标报告仍明确 `sealed_holdout=False`。建议在已有影子观察基础上增加用户级前瞻项目：事先冻结规则、费用、期限、评价指标及比较版本清单，后续自动纳入全部信号；改变参数产生新版本，不覆盖旧结果。展示净期望、区间、盈亏比、回撤、机会保留率与缺失数据，不只展示高胜率。

验收：部分成交不膨胀为多笔独立成功交易；复盘净损益与账户账本一致；失败、未成交、未决均保留；修改未来输入不改变之前已发布信号。此功能不能作为提高未来收益的承诺，也不恢复用户已取消的四项策略绩效硬门槛。

### 5.2 模拟成本、风险额度与跨端确认

PAPER 已考虑公开盘口、合约数量规则、费用和滑点，但明确 `funding_simulated=False`，不模拟强平，也不保证离线期间补成交。优先加真实结算时点的资金费账本、执行偏差和漏观测标记，不必先引入实盘或杠杆。

进一步增加每个用户/每个 MCP 连接的授权范围：账户、币种、单笔金额、每日新增风险、到期时间及暂停新开仓。现有 MCP 权限检查和账户预算应保留，但交易服务目前不按连接身份细分额度。额度应在服务端事务里检查，Web/MCP 不能各自算一份。

新版 TG PAPER 目前只读，不能把旧提案路径的确认当作已覆盖新共账本。后续可让 Web/MCP 创建服务端冻结的待确认意图，TG 显示账户、方向、数量、预计成本和有效期，再由用户确认；模型传入 `confirm_paper=true` 不是 TG 人工确认。

验收：资金费按结算时点真实持仓、幂等记账，缺失费率不当零；跨端重复确认只有一笔委托；过期/撤销/账户不匹配拒绝；确认重新校验行情和资金。暂停新开仓或套餐到期不阻断必要降险操作；只读连接不能借 TG 自动获得交易权限。

- 明确正式部署契约：当前生产 systemd 年度试验 spool 约 167.4MiB，而 `docker-compose.yml:101` 的 research-worker `/tmp` 仅 64MiB、引擎预算最高 512MiB。这是复制部署时的明确不一致，不是已证实当前 systemd 故障。应在目标交付环境中跑相同规模验收。
- CI 已有检查，但 PostgreSQL 专项目前显式列出四组较早集成测试，需将新 PAPER、OAuth/MCP、证据压缩、年度/组合研究及前端构建测试纳入发布流水线；上一轮手动通过不能替代以后持续执行。
- 生产为 PostgreSQL 14，CI 的 Timescale 镜像基于 PostgreSQL 16；要明确支持矩阵并在真实目标版本验收。官方列出 PostgreSQL 14 支持结束日为 **2026-11-12**，应尽早安排与 Timescale 扩展兼容的升级演练，不在线盲升。[PostgreSQL 版本支持政策](https://www.postgresql.org/support/versioning/)
- 第二台大盘机器可先作为冷证据/备份与恢复节点；研究 worker 可在之后独立扩容。主数据库需要稳定低延迟存储，不能简单把跨公网普通磁盘挂载当成数据库高可用。备份节点也不是自动接管节点；副本、连接切换和单写者约束需要单独演练。

## 7. 历史节省空间的后续设计边界

主库优先保留：候选/阶段 ID、模型版本、首次出现/形成/确认/失效时间、当时已知时间、触发/目标/失效价格、原始预测与后续结果、样本归属及去重信息、收益/MFE/MAE/成本、未决/删失原因和原始证据引用。统计需要的逐案例结果不能只折叠成一个总胜率。

较大的原始 JSON、完整几何、引用的 K 线版本及证据图可进入按内容哈希寻址的冷证据层。相同不可变证据可复用，不应为了每次查看、每个用户反复复制。访问权限仍按用户/工作区验证，内容相同不意味着私有分析可跨用户公开。

迁移顺序：按表和时间段测量真实收益 → 小批迁移并校验可还原 → 用新旧读取路径比对样本数/统计/原图 → 再按明确留存授权回收冗余热副本。只有 heartbeat 或未变化观察可考虑去重，不能混淆候选数、观察次数和独立收益样本数，更不能因为失败而丢弃案例。

数据库普通更新/删除后的空间通常首先供数据库复用，不一定立即返还文件系统；本轮没有执行 `VACUUM FULL` 或重建大表。后续是否整理文件，必须结合锁时间、WAL、峰值额外空间和恢复方案单独设计。[PostgreSQL 日常空间维护](https://www.postgresql.org/docs/14/routine-vacuuming.html)

备份、冷证据和缓存采用不同生命周期：备份保障恢复，冷证据保障历史可追溯，缓存保障速度。不能用同一条“超过 N 天删除”规则全部清理。

## 8. 建议实施顺序与发布验收

1. 第一批：容量/异机恢复、用户改密与邀请/成员页、普通成员个人 MCP 权限、用量计量与最低资源预算；并行确认商业数据许可。这批先解决能否持续提供服务。
2. 第二批：交易归因复盘、前瞻观察、PAPER 资金费与用户风险额度、MCP 同时点依据、通知解释与真正收件箱，完善“发现 → 研判 → 模拟 → 复盘”的日常使用。
3. 第三批：套餐支付、支持/导出/退出流程、可重复发布与扩容；在小范围真实用户验收和恢复演练基础上决定公开推广规模。多布局等图表增强可按实际反馈穿插交付。

每批必须分别记录源码测试、隔离数据库测试、真实浏览器测试和生产低风险验收，不混用证据。现有年度合成容量测试不是多租户数据库压力测试，OWNER 通过不等于普通用户通过，MCP 工具读取通过不等于 TG 真正送达。后续任何需要实际下单/发消息/费用或新的服务授权的验证，单独按明确范围执行。

四项策略绩效部署门槛继续保持此前取消的政策；用户风险额度是另一类控制，不借商业化重设这些门槛。本轮没有启用实盘。所有改进的目标是可靠性、可理解性、资源可控和可验证表现，不承诺提高未来胜率或利润。
